# Architecture Decisions — Digital Heroes

Documented assumptions and rationale for choices made during Phase 1.
Each section is intentional and drives the shape of Phases 2–5.

---

## 1. Canvas Library — **Fabric.js** (v6)

**Decision:** Fabric.js for the Web-to-Print designer.

**Rationale**
- First-class JSON serialization (`canvas.toJSON()` / `loadFromJSON`) maps directly to
  the `designs.canvas_json` column and powers one-click reorder from saved designs.
- Native text-editing (`IText`/`Textbox`), image clipping and object bounding
  manipulation needed for enforcing print-zone clamping.
- Simpler SSR-safe mounting — dynamically imported with `ssr: false` at the designer
  route, no hydration-mismatch traps.
- React-Konva would require manual two-way state sync between React and the Konva node
  tree — more error-prone for a proof-critical flow.

**Constraint:** Designer is mounted via `dynamic(() => import(...), { ssr: false })`.

---

## 2. Server-Side Print Pipeline — **pdf-lib + sharp** (no Chromium)

**Decision:** Pure-JS PDF and raster generation. No Puppeteer, no headless browser.

**Rationale**
- Clean Vercel serverless execution within cold-start budgets.
- `pdf-lib` renders text with embedded fonts and image XObjects for PDF output.
- `sharp` handles PNG rasterization at target DPI and pre-compiles for Lambda.
- Deterministic, auditable, replayable — the same draw operations produce byte-identical
  output per configuration.

**Approach**
- Canvas JSON is flattened server-side into an ordered list of draw operations
  (image, rect, text, path) inside `lib/print/pdf-generator.ts` / `png-generator.ts`.
- Bleed and safe-margin expansion is applied at the generator boundary, using each
  product's `bleed_mm` and `safe_margin_mm`.
- Bulk CSV merge splits rows with `papaparse`, runs the fit-rules engine per row,
  generates one PDF per row, and zips with `jszip` under the naming convention
  `OrderID_ProductType_Date_Output`.

---

## 3. RLS Strategy — **Default Deny, Server-Writes-Only for Orders**

**Decision:** All tables have RLS enabled. Customers get **SELECT-only** on their own
orders / order items / designs / proofs. All order and order-item writes happen in
server route handlers using the service-role key after server-side validation.

**Rationale**
- Prevents the anon-key client from ever mutating prices, statuses or totals.
- Server routes re-derive prices from `products` + volume tiers + VAT; client prices
  are UX-only.
- Order numbers are generated by a `DEFAULT` sequence, never by the client.
- Admin-only tables (`print_jobs`, production artifacts) are 403-locked at both the
  RLS layer and the route layer.

**Trade-off**
- Every cart → order transition costs one server round-trip to `/api/checkout`.
  Acceptable for a print ordering flow where the user is already pausing to review.

## 4. Proof Lifecycle — **Versioned, Auto-Superseding, Immutable Log**

**Decision:**
- A `BEFORE INSERT` trigger on `proofs` sets any prior `pending` proof for the same
  `order_item_id` to `superseded` — there is always exactly one live proof per item.
- A `BEFORE UPDATE` trigger enforces that only the latest version may be approved or
  rejected, and stamps `approved_at` server-side.
- The `uploaded` event is auto-logged by an `AFTER INSERT` trigger.
- `approved` / `rejected` / `change_requested` log entries are written explicitly by
  `/api/proofs/[proofId]/decision` with a **server-verified** `user_id` and free-text
  notes. Removing the auto-logging for state changes ensures no orphaned logs without
  notes and eliminates a class of spoofing risks.
- `proof_logs` has no UPDATE/DELETE policies — the trail is append-only by omission.

## 5. Hard Print-File Gate — **Trigger + Route + Storage**

Three independent layers prevent accidental print-file generation against an
unapproved proof:

1. **DB trigger** (`enforce_approved_proof_for_print_job`) raises on any
   `print_jobs` INSERT whose referenced proof is not `approved`.
2. **API route** (`/api/print/generate`) returns `403 Locked` when
   `latest_proof.status !== 'approved'`.
3. **Storage bucket `print-jobs`** has admin-only RLS — no customer can ever
   enumerate or download production artifacts, even with a URL.

## 6. Order Writes Go Through Server Routes

**Decision:** Customers cannot `INSERT`/`UPDATE`/`DELETE` rows in `orders` or
`order_items` directly.

**Consequences**
- Client cart is a proposal only.
- Server validates: product exists + active, quantity > 0, dimensions within product
  bounds, material allowed, orientation allowed, VAT consistent.
- Server creates the order and its items atomically (single DB transaction via the
  service role) and then redirects to Stripe Checkout.
- Stripe webhook flips `status = 'order'` (from `quote`) and stamps `paid_at` and
  `stripe_payment_intent_id`.

## 7. Xero Export — **Incremental, Idempotent**

**Decision:** `orders.xero_exported_at` marks each export run. Subsequent exports
only include `status = 'completed' AND xero_exported_at IS NULL`. The returned
`xero_invoice_id` is stored back to the order.

**Rationale**
- Prevents duplicate invoice imports in Xero.
- `products.xero_account_code` defaults to `'200'` (typical revenue account) and is
  per-product overridable — some divisions may legitimately post to different codes.
- CSV shape follows Xero's Sales Invoice import template (contacts, line items,
  account code, tax type, totals).

## 8. Storage Buckets & Path Conventions

| Bucket              | Public | Path convention                                  | Read policy              |
| ------------------- | ------ | ------------------------------------------------ | ------------------------ |
| `customer-artworks` | no     | `{user_id}/{design_id}/{filename}`               | owner + admin            |
| `proofs`            | no     | `{order_item_id}/v{n}.pdf`                       | owning customer + admin  |
| `print-jobs`        | no     | `{order_item_id}/{order_number}_{slug}_{date}.*` | **admin only**           |
| `gallery`           | yes    | `{division_slug}/{filename}`                     | public                   |

- Bucket-scoped RLS policies key off `storage.foldername(name)` so path traversal
  outside the caller's folder is impossible at the database level.
- Server-generated production artifacts always live in `print-jobs`, never
  `customer-artworks`, so a customer can never see them.

## 9. Pricing Model

- **Base price** (cents, per unit) on `products.base_price_cents`.
- **Area adjustment**: unit price scales with `(widthMm × heightMm)` relative to the
  product's minimum area, floored at `base_price_cents × 1.0` (no negative adjustments).
- **Material multiplier** applied next: `areaAdjusted × material.priceMultiplier`.
- **Volume discount**: highest matching tier from `volume_discount_tiers` wins; tiers
  do **not** stack.
- **VAT**: applied to the discounted line total; per-product `vat_percent` — mixed-rate
  orders are rejected to keep invoices simple.
- All money is integer cents. The client calculator mirrors the server algorithm
  exactly (via the shared `src/types/pricing.ts` contract) but the server is the
  authority and recomputes every number.

## 1. Canvas Library — **react-konva** (superseded Fabric.js)

**Decision:** The Web-to-Print designer uses **react-konva**.

**Rationale (revised)**
- Phase 3 explicitly requires `<Group>` clip semantics, `<Transformer>` bound-box
  enforcement (`boundBoxFunc`) and `dragBoundFunc` — all native Konva primitives
  with first-class TypeScript types.
- `next/dynamic(..., { ssr: false })` + `webpack externals: { canvas: 'canvas' }`
  gives clean builds on Vercel without pulling `node-canvas` into the server bundle.
- The saved `canvas_json` is now a plain JSON of our own element model
  (`{ elements, print_area, canvas_width_px, canvas_height_px }`) rather than a
  library-specific serialisation — future-proof for Phase 4 server-side rendering.

**Constraint:** The designer route is a Server Component that dynamically imports
`DesignerWorkspace`, which in turn dynamically imports `Canvas` with `ssr: false`.

## 14. Konva drag/resize constraint model

Every element position is stored as a **center** (`x`, `y`) plus `width`, `height`,
`rotation` and rendered with `offsetX = width/2, offsetY = height/2`. This makes
rotation around the element's centre natural.

The clamping rule is a **rotation-aware AABB** inside `print_area`:



Applied in `dragBoundFunc` (live drag) and again in `onTransformEnd` (resize/rotate).
`Transformer.boundBoxFunc` additionally rejects any resize whose target box exceeds
the print area. Result: users cannot drag, resize or rotate outside the printable zone.

## 15. Signed-URL strategy for private artwork

`customer-artworks` is a private bucket. `canvas_json` element `srcPath` and
`designs.uploaded_artwork_url` persist **storage paths**, never signed URLs.
Signed URLs (4-hour TTL) are generated server-side on designer load and client-side
after upload, used only for rendering. Thumbnails follow the same pattern
(`thumbnail_url` = storage path, signed on read).

## 16. Design ID lifecycle

The client receives a `crypto.randomUUID()` on first mount (`/designer/[productId]`
without `?designId`). Uploads use this ID in the storage path
`{user_id}/{design_id}/{filename}`. On save, `/api/designs` insert-or-updates with
that same ID. RLS restricts the storage folder to `auth.uid()`, so cross-tenant
paths are impossible.

## 17. Print engine — pure Node, no headless Chrome

PDF via `pdf-lib` (pure JS), PNG via `sharp` + SVG composition, ZIP via
`jszip`. All three run in the Node.js runtime on Vercel with no Chromium
dependency. Endpoints pin `export const runtime = 'nodejs'`.

Coordinate mapping
------------------
- Page dimensions = `(widthMm + 2*bleed_mm) × (heightMm + 2*bleed_mm)`,
  converted to points at **2.83465 pt/mm** (per phase spec).
- Canvas pixels map linearly: `scaleX = pageWidthPt / canvas_width_px`,
  `scaleY = pageHeightPt / canvas_height_px`. Separate axes are used so the
  canvas is not distorted even when the template aspect ratio slightly
  diverges from the physical trim; content outside the trim becomes bleed.
- Element positions are stored as **centers** with rotation. PDF rendering
  computes the baseline offset so rotated text and images rotate around the
  element's visual center.

Text fitting
------------
- `template-fit.ts` is applied identically for the browser preview (Phase 3)
  and the server render (Phase 4) via an injected `TextMeasurer`.
- Server measurer uses embedded pdf-lib `StandardFonts`; the browser measurer
  uses an offscreen canvas. Metrics differ by <2% in practice.
- `letterSpacing` is accounted for in the fit calculation (making the fitted
  fontSize slightly smaller), but is **not** rendered on the PDF text itself —
  pdf-lib's `drawText` lacks a public letter-spacing option. Text therefore
  renders slightly tighter than the fit box, which is strictly safe (never
  overflows). SVG (PNG path) **does** honour letter-spacing.

Fonts
-----
- pdf-lib `StandardFonts` are WinAnsi-only. `sanitizeForWinAnsi()` decomposes
  diacritics (e.g. `ā → a`) and replaces unmappable code points so PDF
  generation never throws on user input.
- Production follow-up: embed Inter via `@pdf-lib/fontkit` to preserve
  macrons and full Unicode end-to-end.

## 18. Approval gate — three independent layers

1. **Route handler (this phase)** — queries `proofs` for
   `status = 'approved'` before doing any work and returns **403**
   with the exact message `Production files are locked until the customer
   approves the proof.` if none is found.
2. **DB trigger** `enforce_approved_proof_for_print_job` (Phase 1) — raises
   on any `print_jobs` INSERT whose `proof_id` is not `approved`. Cannot be
   bypassed from the client even with the service-role key.
3. **Storage bucket `print-jobs`** — admin-only RLS. Even if a signed URL
   leaks, the owner check lives at the object level.

The route checks **latest approved**, not "any approved" — once a newer proof
exists that superseded the previously approved one, generation is locked
again until the new one is approved.

## 19. Proof decision semantics

`POST /api/proofs/[proofId]/decision` accepts only
`{ decision: 'approved' | 'rejected', notes?: string }` from the owning
customer (verified twice — RLS + explicit ownership check in the handler).

Action mapping for `proof_logs`:

| decision     | notes        | `action`            |
| ------------ | ------------ | ------------------- |
| `approved`   | any          | `approved`          |
| `rejected`   | non-empty    | `change_requested`  |
| `rejected`   | empty/missing| `rejected`          |

`proof_logs` RLS restricts customer inserts to `action = 'change_requested'`.
The route therefore inserts `approved` and `rejected` log rows via the admin
client **after** verifying ownership; the customer-facing RLS still forbids
those action names if the client bypassed the route.

On `approved`, the handler advances `order_items.production_status` to
`production`, and promotes `orders.status` to `production` once *every* item
in the order is in `production` or `completed`.

## 20. Supersede is a DB guarantee

`supersede_pending_proofs()` (BEFORE INSERT on `proofs`) flips any prior
`pending` proof for the same `order_item_id` to `superseded`. The upload route
does not perform this transition itself — that keeps the invariant
enforceable by the database alone.

## 21. CSV merge naming

Folder and file names follow the spec exactly:

`YYYYMMDD` is UTC. `index` is 1-based. `OrderNumber` is the DB-generated
`DH-YYYY-#####` string from `orders.order_number`. Rows that fail PDF
generation are skipped, logged, and counted in `metadata.skippedRows` — the
ZIP is still produced with the successful rows.

## 22. CSV merge capacity

`MAX_ROWS = 500` rows and `MAX_CSV_BYTES = 5MB`. Batches over that budget
should be routed through a background queue (Inngest / QStash) rather than a
synchronous serverless invocation — the ZIP is built in memory and uploaded
to `print-jobs`, so extremely large merge jobs would exceed function
memory/time. This is a documented constraint, not an oversight.

## 23. PNG pixel budget

`MAX_PIXELS = 32,000,000` per image. If the requested physical dimensions at
`target_dpi` exceed that, the effective DPI is reduced (and reported in
`print_jobs.metadata.effectiveDpi`) rather than throwing. Typical jobs —
A4, A3, race bibs, plaques — never hit this cap.

## 24. Thumbnail & proof URL strategy

Private buckets (`proofs`, `print-jobs`) return **signed URLs** with short TTLs
(2 hours for customer previews, 24 hours for admin download responses).
Storage paths — not signed URLs — persist in the database. Anything that
needs to survive a page reload re-signs on demand.
